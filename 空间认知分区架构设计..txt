空间认知映射与分区维护单元架构规范

---

一、项目空间结构

1. 根模块目录（app 根模块）

```
com.example.app
├── data/
├── di/
├── navigation/
├── screen/
├── theme/
├── MainActivity.kt
└── MyApplication.kt
```

2. 页面模块目录（以 musicplayer 页面为例）

```
screen/
└── musicplayer/
    ├── portrait/
    ├── landscape/
    ├── MusicPlayerScreen.kt
    ├── MusicPlayerUiState.kt
    └── MusicPlayerViewModel.kt
```

3. 方向布局内部结构（竖屏 & 横屏）

竖屏布局（portrait/）——三个分区

```
portrait/
├── topPanel/
│   └── coverimage/       ← UI代码+功能代码同目录
├── middlePanel/
│   ├── songinfo/
│   └── progressbar/
├── bottomPanel/
│   └── playbackcontrols/
└── PortraitAssembly.kt   ← 组装
```

横屏布局（landscape/）——三个分区

```
landscape/
├── leftPanel/
│   └── coverimage/
├── rightPanel/
│   ├── songinfoheader/
│   └── lyricsscroll/
├── bottomPanel/
│   ├── progressbar/
│   └── playbackcontrols/
└── LandscapeAssembly.kt
```

4. 数据层拆分结构

```
data/
├── repository/   ← 协调各数据来源
├── remote/       ← 网络数据
├── local/        ← 本地数据库
└── cache/        ← 内存或磁盘缓存
```

---

二、数据流与闭环

1. 事件流（向上）
      UI（用户操作） → ViewModel → Repository
2. 状态流（向下）
      Repository（数据结果） → ViewModel（生成State） → UI（监听并刷新）
3. 完整闭环
      用户操作 → ViewModel → 数据层 ⇄ 数据层 → ViewModel → UI状态 → 界面刷新

---

三、命名与组织原则

· 空间认知优于抽象思维：分区命名遵循“空间结构映射 + 语义命名”，例如：顶部分区、中部分区、底部分区；顶部工具栏、左侧导航栏、中部工作区、右侧协作区。
· 分区数量遵循真实视觉边界：示例中的分区数量（如 3 分区）仅为结构演示，实际页面应根据真实视觉布局确定分区数量。禁止为凑齐固定数量而强行拆分或合并视觉区域。
· 目录即认知路径：任何代码应能通过目录路径快速定位，而非根据抽象关系推导位置。
· 空间结构一旦确定，不因实现方式变化而改变。

---

四、维护单元定义

每个维护单元（最小组织单位）必须满足：

· 单一职责
· 单一决策
· 单一路径
· 独立维护
· 可独立删除
· 可独立替换

任何维护单元均不应依赖其内部实现细节之外的内容。

---

五、架构设计原则

1. 复杂度管理原则

复杂度只能通过继续拆分维护单元降低，不通过增加抽象层隐藏。
当某维护单元承担多个职责、多个决策或难以快速理解时，应继续拆分为更小的维护单元，而非引入新的架构层、基础类或业务抽象。
拆分优先于抽象。

2. 抽象使用原则

仅允许对天然公共能力进行抽象，即与业务、页面、功能无关的基础能力实现，包括：

· 网络
· 数据库
· 图片加载
· 文件读写
· 权限管理
· 日志
· 时间与格式化工具

禁止：

· 因代码相似而抽象
· 建立 BaseXXX、CommonXXX、ManagerXXX 等业务抽象
· 建立仅为复用而存在的中间层

复用优先采用独立实现，其次采用组合，而非继承与抽象。

天然公共能力存放于根模块下的独立目录（杜绝万能目录）：

```
data/ database/ network/ image/ permission/ storage/ logger/ di/ navigation/ screen/ theme/
```

3. 数据层拆分原则

· Repository 负责统一数据访问，不负责数据来源实现。
· 数据来源按职责拆分：Remote、Local、Cache。
· 任何数据来源变化，不应影响上层维护单元。

4. 组合优先原则

· 页面由维护单元组合形成，维护单元由更小维护单元组合形成。
· 组合关系清晰可见，不隐藏于继承体系或抽象层中。
· Assembly 仅负责组合，不承担业务决策。

5. 架构演进原则

项目规模增长时，仅允许通过以下方式扩展：

· 新建维护单元
· 拆分维护单元
· 增加天然公共能力

禁止通过增加新的业务架构层解决复杂度问题。
架构规模增长不应改变整体认知方式。

6. 可预测性原则

相同类型的问题，应始终采用相同的组织方式解决。
新增功能时，不重新设计架构，不创造新的目录形式，不引入新的抽象模式，而是在既有空间结构内继续拆分、继续组合。
项目整体应保持长期稳定的认知模型。

---

六、技术栈与约束

· 技术栈：Kotlin + Koin + Jetpack Compose + 单一 Activity
· 禁止任何形式改变本规范中的包结构与细分原则。
· 空间路径、单一职责、单一决策、最小化可维护单元为不可变约束。
